Developer notes — do not include on real pages

Prototype login behaviour: the username and password fields are visual examples only. In this prototype, pressing Login always opens the supplied dashboard even when either or both fields are blank. A blank username uses CK223 as the display alias. The password is not checked, saved or transmitted. This permissive click-through must exist only in the prototype.

Production learner authentication: the real application must require a genuinely registered username and password. Submit credentials over HTTPS to a server-side authentication endpoint, reject blank or invalid credentials, confirm that the account is active, compare the password with a strong salted password hash, rotate the session identifier after login and issue only a secure, HttpOnly, SameSite cookie. Never place passwords, password hashes or reusable session tokens in localStorage.

Single-account session rule: the production backend must allow only one active session per learner account. Keep an authoritative session record containing user ID, session ID, sign-in time, last activity time, expiry, device/browser summary and coarse IP-derived region. When the account already has a valid active session, reject a second login and explain that the account is already in use; do not silently create a second session. The administrator console must be able to view the session and force it to end. Device or location data should be proportionate, coarse and covered by the privacy notice rather than used as precise tracking.

Inactivity protection: after five minutes without meaningful keyboard, pointer, touch or navigation activity, display an “Are you still there?” prompt. Give the user two minutes to continue the session. Continuing must refresh the server-side session; no response must revoke the session on the server, clear the cookie and return the learner to the production login page. The server must remain authoritative so closing or modifying browser JavaScript cannot keep an expired account active.

Suspended and reactivated accounts: a suspended account must be blocked at authentication. Under the required product policy, suspension also erases the learner’s saved quiz attempts, exam attempts, answers, feedback, progress summaries and derived performance data. Reactivation restores account access only and starts a new empty learner-data profile; it must not restore the erased records. The destructive suspension action needs an explicit administrator confirmation, a database transaction and an audit entry.

Data supplied after login: the authenticated session should provide only the learner’s pseudonymous account ID, username/alias, role, access status and permissions. Dashboard, Practice, Exams and My Performance should then request the learner’s saved attempts and performance records from protected backend APIs. Every request must be authorised against the signed-in account rather than trusting a user ID supplied by the browser.

Production operations: configure secrets through protected environment variables, enforce HTTPS, CSRF protection, rate limiting, login throttling and generic error messages, and add monitoring for repeated failed logins and concurrent-session attempts. Keep database backups, migration rollback plans, retention rules and a tested account/data deletion process. Use a staging environment before deploying changes to the Cloudways-hosted production application.
